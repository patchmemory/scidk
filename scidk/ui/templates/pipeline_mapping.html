What the page produces is a mapping config in the format scidk/pipeline/mapping_schema.json specifies and MappingEngine consumes — the acceptance criterion is that the engine takes it unmodified, so the page reports the engine's own validation rather than deciding for itself what "complete" means. Three things about the format that shape the whole UI: * A node mapping's `id` is what the task description calls a *role*. Two entries may share a `label`, and `relationship_mappings` reference entries by id, not by label — that is how one row produces both a PI Person and a submitter Person with different relationships. So a "role" here is a whole mapping block, and every relationship needs a role at *both* ends, not just the From end. * The merge key is a *property*, not a column. The key column is whichever column is assigned to the key property, which is why the key control is a property selector with its column beside it rather than a second column dropdown. * Two node forms exist. Column-per-property is the common one. When one column expands into several properties — "Jane Smith " is a name *and* an address — the format uses `source` plus `property_map`, and a transform whose return annotation says it produces an object is only offered there. What this page deliberately does not edit, per the task's out-of-scope list: `column_resolution` (the _sp/_orig transforms, which take no cell value at all and so cannot attach to a column), property `fallback`, `row_filter`, `condition`, `options` and `vocabulary_check`.
